# Aurum Agent 阶段六：企业级加固开发方案

> 方案日期：2026-08-02  
> 前置基线：阶段五已完成，Git 基线 `571192d`，回答图 `finance-agent-p5.6-v1`，
> 数据库迁移头 `20260802_0012`  
> 方案定位：先完成可运行、可观测、可恢复、可回退的单机生产基线，不追求一次覆盖大型企业平台能力

## 1. 阶段目标

阶段六不新增自然语言记账、财务写工具或新的业务页面，主要把阶段五的功能闭环加固为
可以受控上线和持续运维的版本。完成后系统至少应具备：

- 用户和模型资源有上限，异常流量不会无限消耗模型费用或拖垮服务；
- 日志、Trace 和指标能够定位一次 API、Agent、检索、工具和模型调用；
- 日志及观测数据不包含 Token、密钥、完整财务明细和未脱敏文档内容；
- 至少一个高收益读取链路具备安全缓存，并可正确失效和降级；
- RAG、Prompt Injection 和跨用户隔离进入版本化回归门禁；
- 有可重复执行的压力测试、备份、恢复、灰度发布和回滚流程；
- 每项能力均有自动化验证或演练记录，而不是只保留设计文档。

## 2. 当前基础与主要缺口

| 能力 | 当前基础 | 阶段六缺口 |
| --- | --- | --- |
| 身份与隔离 | JWT、Refresh Token 轮换、登录限流、应用层过滤、PostgreSQL RLS | 保持回归，补资源耗尽与越权攻击场景 |
| 审计 | `audit.audit_logs`、Agent 工具调用和财务证据已持久化 | 统一日志脱敏规则、保留周期和访问边界 |
| 请求关联 | API 已生成 `request_id`，Agent Run 已有 `trace_id` 字段 | 使用上下文自动传播，接入 OpenTelemetry |
| 运行指标 | 消息、检索、Agent 和工具表已有 Token、延迟等字段 | 缺 Prometheus 指标、Grafana 面板和告警 |
| Redis | 已用于登录安全状态、撤销和 Celery | 缺通用配额、并发控制与业务缓存 |
| RAG/Agent 质量 | 阶段五确定性评测 16/16，已有引用和数值 Grounding | 缺 RAG 黄金集、注入攻击集和发布回归阈值 |
| 部署运维 | 开发 Compose、健康检查和部署指南已存在 | `deploy/` 中尚无生产配置、备份恢复和发布脚本 |

阶段六沿用现有 PostgreSQL、Redis、MinIO、Celery、FastAPI 和 Vue 技术栈，不在本阶段
引入 Kubernetes、独立日志平台、多地域容灾或多模型路由。

## 3. 总体方案

```text
浏览器
  -> Gateway（HTTPS、灰度路由、仅暴露 Web/API）
  -> FastAPI（请求上下文、配额、指标、Trace）
       -> LangGraph / 财务工具 / RAG
       -> 模型、Embedding、Reranker
       -> PostgreSQL（业务真相、审计、用量事实）
       -> Redis（限流、并发租约、短期缓存）
       -> MinIO（源文件）
  -> OpenTelemetry Collector -> 可选 Trace 后端
  -> Prometheus -> Grafana

备份任务 -> PostgreSQL 备份 + MinIO 对象/清单 + 加密异地副本
发布脚本 -> 候选实例 -> 冒烟/小流量 -> 切换 -> 可回退旧版本
```

实施顺序采用“先看得见，再控制资源，再建立门禁，最后演练运维”。阶段六拆分为 P6.1～
P6.5，每批都保持现有 API 和前端兼容，且完成后才进入下一批。

## 4. 开发批次

### P6.1：日志脱敏与可观测性底座

> 状态：已于 2026-08-02 完成基础实现与本地容器验收。实现证据见
> [P6.1 验收报告](./aurum-agent-phase-6-p6.1-acceptance.md)。

先建立后续配额、缓存和压力测试所需的测量能力。

主要开发：

- 建立统一请求上下文，通过 `contextvars` 自动传播 `request_id`、`trace_id`、
  `conversation_id` 和 `agent_run_id`；用户标识只输出不可逆哈希；
- 将结构化日志改为字段白名单，增加统一脱敏过滤器；过滤 Authorization/Cookie、JWT、
  API Key、数据库 URL、银行卡号、流水描述、用户问题全文和文档正文；
- 异常日志保留错误类型和安全错误摘要，不直接序列化请求体、模型 Prompt 或 Provider 响应；
- 接入 OpenTelemetry，覆盖 FastAPI、SQLAlchemy、Redis、模型 Provider、Retriever、
  财务工具和 Celery；默认不记录 Prompt、回答、财务结果与文档内容；
- 提供 Prometheus `/metrics`，由生产网关限制为内网访问；指标标签禁止使用 `user_id`、
  会话 ID、问题文本等高基数或敏感值；
- 增加最小 Grafana 面板：服务健康、Agent/RAG/模型、文档任务与队列；
- 增加基础告警：API 5xx、模型失败、Worker 离线、队列积压、数据库连接池、备份失败；
- Trace 导出保持可配置，开发环境可关闭，生产环境先采用低比例成功采样并保留错误 Trace。

建议代码位置：

```text
app/observability/context.py
app/observability/logging.py
app/observability/metrics.py
app/observability/tracing.py
deploy/otel-collector/
deploy/prometheus/
deploy/grafana/
```

验收要点：

1. 给定密钥、Token、银行卡号、流水描述和 Prompt 的测试日志中不出现原文；
2. 一次聊天请求可用同一 Trace 串联 API、Agent、检索、工具和模型 Span；
3. `/metrics` 可采集请求量、延迟、SSE、模型 Token、检索、工具、Worker 和缓存指标；
4. 指标标签基数受控，关闭 Trace 导出时不影响业务请求；
5. Grafana 能展示真实冒烟请求，至少一条测试告警可被触发和恢复。

### P6.2：用户/模型配额与最小安全缓存

> 状态：已于 2026-08-02 完成基本实现与本地 Redis 验收。实现证据见
> [P6.2 验收报告](./aurum-agent-phase-6-p6.2-acceptance.md)。

配额采用 Redis 原子计数和并发租约，PostgreSQL 中现有消息及 Agent Run 记录继续作为实际
Token 和调用结果的审计事实。第一版使用环境配置的统一策略，不开发复杂计费、套餐和管理
后台。

配额至少覆盖：

- 单用户每分钟问答次数、每日模型 Token 和同时运行的 Agent 数；
- 全局模型每分钟请求数、Token 预算和并发数；
- 文档上传次数/容量和处理中任务数；
- 请求前预留预算，完成后按 Provider 实际用量结算，失败或取消时释放并发租约；
- 超限统一返回稳定错误码、HTTP 429 和 `Retry-After`，SSE 在启动模型调用前拒绝；
- Redis Lua 脚本保证多 API 实例下检查与占用原子化，租约必须有 TTL 防止异常泄漏；
- 模型调用和上传等高成本入口在配额存储不可用时拒绝新任务，普通只读财务 API 可降级运行。

缓存第一版只做容易保证一致性的读取路径：

- 优先缓存已发布知识库的检索结果；Key 包含项目/知识库版本、查询哈希、Embedding、
  Reranker 和检索参数版本；
- 如基准测试表明确认有收益，再缓存个人财务聚合；Key 必须包含用户、统计区间、币种和
  财务数据版本，任一财务写操作后递增版本使旧缓存自然失效；
- 不缓存最终 LLM 回答、Access/Refresh Token、完整流水明细、Checkpoint 和 SSE 内容；
- TTL 使用短周期加随机抖动，并设置单飞锁避免缓存击穿；Redis 故障时缓存旁路，不影响
  数据库真相和引用校验；
- 所有命中仍执行当前用户、项目权限和引用有效性检查。

建议代码位置：

```text
app/governance/quotas.py
app/providers/quota_store.py
app/providers/cache.py
app/services/retrieval.py
app/config.py
```

验收要点：

1. 并发请求不能绕过用户和全局配额，超限响应不产生模型费用；
2. 正常完成、失败、取消和进程异常后，配额结算或租约过期行为正确；
3. 缓存 Key 不含问题和用户敏感原文，用户 A 无法命中用户 B 的私有结果；
4. 知识发布/停用及财务写入后不会返回陈旧数据；
5. Redis 故障时缓存可旁路，配额按既定高成本入口策略安全失败；
6. Prometheus 能展示配额拒绝、当前并发、缓存命中率和缓存耗时。

### P6.3：RAG、安全与性能回归门禁

> 状态：已于 2026-08-02 完成基础实现与本地验收。真实 Provider 与完整单机发布负载需在
> 候选测试环境补录证据，详见
> [P6.3 验收报告](./aurum-agent-phase-6-p6.3-acceptance.md)。

建立两级质量门禁，避免真实模型的波动和费用阻塞普通开发：

- PR 门禁使用固定数据、Fake Provider 和确定性规则，必须稳定重复；
- 候选发布在测试环境使用真实 PostgreSQL、Redis、MinIO 和模型 Provider，按版本化阈值验收。

新增版本化数据集：

- `evals/phase6-rag-regression.json`：覆盖可回答、无答案、冲突文档、多版本、跨知识库、
  混合财务问题和引用定位；
- `evals/phase6-prompt-injection.json`：覆盖用户直接注入、文档间接注入、索取系统 Prompt/
  密钥、伪造引用/工具/用户身份、诱导写操作和越权检索；
- 继续运行阶段五评测，确保财务数值 Grounding、只读工具和风险提示不回退。

核心指标：Retrieval Recall@K、引用有效率、引用覆盖率、Groundedness、拒答准确率、财务
数值正确率和跨用户泄漏数。引用有效率、财务数值正确率和隔离攻击阻断率必须为 100%；
召回与回答类指标在首次稳定基线后锁定阈值，后续发布不得静默降低。

压力测试至少包含普通 API、RAG 检索、带 Fake Provider 的 SSE、真实模型小流量冒烟和
文档入库/积压恢复。将 `local-smoke` 与 `single-node-release` 两套负载配置版本化，记录
吞吐、P50/P95/P99、首字延迟、5xx、连接池、队列和模型错误。正式容量目标尚未确认，
因此本阶段先要求目标负载下无跨用户泄漏、无资源持续增长、5xx 低于 1%，并将 P95 相对
已锁定基线的回退控制在 20% 内；这不是最终生产容量承诺。

验收要点：

1. 三套阶段五/阶段六评测可由统一命令执行并输出机器可读报告；
2. Prompt Injection 不改变系统指令、不产生写工具调用、不泄露身份或跨项目内容；
3. 真实 Provider 评测保存模型、Prompt、Embedding、Reranker 和数据集版本；
4. 压测可重复运行，结果、配置和基线随发布归档；
5. 配额、超时、停止生成、缓存失效和 Provider 降级均进入故障场景测试。

### P6.4：备份、恢复与数据保留

> 状态：已于 2026-08-02 完成单机基础实现与隔离恢复演练；生产外部密钥、真实异地介质及
> 恢复后的真实 Provider 冒烟留待 P6.5 候选环境接入。证据见
> [P6.4 验收报告](./aurum-agent-phase-6-p6.4-acceptance.md)。

阶段六先按单机生产基线定义目标：默认 RPO 24 小时、RTO 4 小时，后续可根据真实业务
要求收紧。PostgreSQL 和对象存储是权威数据；Redis 仅保存可重建状态，不作为唯一备份源。

主要开发：

- 提供 PostgreSQL 加密全量备份脚本、校验和、保留策略和异地复制接口；
- 备份 MinIO 原始文档、对象版本及对象清单，校验数据库对象键和文件哈希；
- 安全备份生产配置清单、镜像/提交/迁移/模型版本和密钥标识；密钥值由外部密钥系统保管，
  不写入备份日志或仓库；
- 提供恢复脚本，将数据恢复到新的数据库和存储桶，禁止直接覆盖唯一生产实例；
- 恢复后自动检查 Alembic Head、RLS、用户/会话/财务/文档计数、对象哈希、引用打开、
  Checkpoint 解密和核心冒烟；
- 定义聊天、审计、检索日志、Trace、指标和备份的保留周期；删除或归档任务必须可审计；
- 备份每日自动执行，至少完成一次从备份到新实例的完整恢复演练并记录 RPO/RTO。

建议资产：

```text
deploy/scripts/backup.ps1（或目标 Linux 环境的 backup.sh）
deploy/scripts/restore.ps1（或 restore.sh）
deploy/scripts/verify-restore.*
deploy/backup-policy.md
```

验收要点：备份失败可告警，备份可校验且不包含明文密钥；恢复环境通过迁移、RLS、对象、
引用、财务汇总和聊天冒烟；演练结果满足阶段默认 RPO/RTO。

### P6.5：生产部署、灰度发布与回滚

> 状态：工程开发与本地蓝绿/回滚演练已完成（2026-08-02）。正式公网切流不属于开发机
> 验收范围，结果见 [P6.5 验收报告](./aurum-agent-phase-6-p6.5-acceptance.md)。

在现有部署指南基础上补齐可执行资产，第一版使用单机 Docker Compose 的蓝绿/小流量发布，
不引入 Kubernetes。

主要开发：

- 增加生产 Compose、Web 构建、Gateway 配置、只读内部网络和 Prometheus/Grafana 配置；
- 镜像使用 Git SHA 不可变标签，构建阶段生成依赖清单并执行 Python、npm 和容器漏洞扫描；
- CI 依次执行 Ruff、Mypy、Pytest、Alembic、前端检查/构建、阶段评测、镜像构建和冒烟；
- 发布前自动创建可验证备份，数据库迁移遵守 Expand-Migrate-Contract 且只由一次性任务执行；
- 候选版本先在独立实例启动，通过就绪、迁移、评测和浏览器冒烟后，仅向测试账号或小比例
  流量开放；观察错误率、P95、模型失败、队列和业务校验后再全量切换；
- SSE 发布时停止接收新长连接并给旧连接留出排空窗口；
- 保存上一镜像、配置和迁移版本，一条命令将网关切回旧实例；数据库默认前滚修复，不自动
  执行破坏性 `downgrade`；
- 完成一次发布成功演练和一次人为制造异常后的自动/人工回滚演练。

阶段六不要求全自动生产发布。生产切流和回滚保留人工批准，但检查、记录和命令必须可重复。

验收要点：

1. 候选版本不接收正式流量时即可完成迁移兼容性与冒烟验证；
2. 灰度指标超过阈值时停止扩流并切回旧实例；
3. 回滚后旧版本健康、核心功能可用、已有数据不丢失；
4. 发布记录包含 Git、镜像、迁移、模型/Prompt、配置、备份、评测和操作人；
5. 生产环境只暴露 Gateway，API 文档、数据库、Redis、MinIO 管理端和 `/metrics` 不对公网开放。

## 5. 阶段完成标准

以下条件全部满足才将阶段六标记为完成：

1. 原阶段六未完成项均有实际实现和验收证据：配额、日志脱敏、缓存、OpenTelemetry、
   Prometheus/Grafana、RAG 回归、Prompt Injection、压力测试、备份恢复及灰度回滚；
2. 阶段一至五的全部质量门禁继续通过，财务 Agent 写工具数仍为 0；
3. 自动化测试未发现跨用户、跨项目或跨知识库数据泄漏；
4. 高成本入口有用户、全局和并发上限，超限不会继续调用模型；
5. 日志、指标和 Trace 通过敏感数据及高基数检查；
6. 至少一个真实读取链路实现可测量的缓存收益，且失效、隔离和 Redis 降级正确；
7. 版本化 RAG 与注入评测达到锁定阈值，真实环境小流量验收通过；
8. 压测未出现持续资源泄漏，满足阶段六锁定的单机发布基线；
9. 从备份恢复到新环境并通过业务校验，RPO/RTO 有演练记录；
10. 蓝绿/灰度发布和回滚各完成至少一次演练；
11. 更新总体方案、架构、部署指南、当前交接和阶段六验收报告。

## 6. 明确不在阶段六实现

- 自然语言记账、预算修改、流水删除、持仓调整等 Agent 写操作；
- 复杂计费、套餐购买、账单结算和配额管理后台；
- 多模型智能路由、本地大模型和多 Provider 自动容灾；
- Kubernetes、多地域双活、跨云灾备和自动弹性伸缩；
- 全量缓存所有问答或长期保存用户 Prompt；
- 自建完整日志检索平台；初期使用容器日志、Trace 后端和 Grafana 即可。

这些能力继续留在阶段七或真实规模、合规和预算明确后的专项阶段。
