# Aurum Agent 长期记忆功能最终开发计划

> 形成日期：2026-08-13  
> 目标分支：`agent-memory-development`  
> 适用基线：个人财务档案前后端闭环已合入 `master`，Agent V2 已支持同一会话最近消息、
> PostgreSQL Checkpoint、只读财务工具和个人知识检索，但尚无跨会话长期记忆。  
> 参考交互：借鉴 Origin 的“聊天中以自然语言明确要求长期保存、档案中可管理、后续问答可调用”
> 产品模式；不复制其实现，也不放宽 Aurum 既有的数据隔离、财务事实和写操作安全边界。
> 方案修订：M2 采用“专用模型负责语义决策和结构化提案、服务端负责受控执行”，不建设大规模
> 本地关键词或句式检测器；模型发出的 Function Call 仅表示操作提案，不代表写入已经完成。

## 1. 最终目标

本专项完成后，用户能够在 Agent 对话框中输入：

```text
请记住：我的年收入税前 30 万美元，平均每年开销 4.5 万美元。
```

系统应完成以下闭环：

1. 由专用模型只根据当前用户消息判断 `save`、`confirm` 或 `ignore`，不依赖海量本地关键词和句式；
2. 模型将待保存内容拆成一至多条结构化提案，服务端校验、去重后写入当前用户的长期记忆；
3. 在同一回答中明确列出“已记住”的内容，并可继续给出简洁、相关的分析；
4. 在后续任意会话遇到相关问题时，自动检索并调用已启用的记忆；
5. 用户可在“个人财务档案 → AI MEMORY”中查看、搜索、编辑、停用和删除记忆；
6. 用户关闭记忆后，Agent 不再保存或调用长期记忆，但既有数据保留，重新开启后恢复可用；
7. 每次保存和调用均可审计、可去重、可追踪，且不能跨用户泄漏。

首版只实现“模型判断用户已明确要求长期保存”或“用户确认待保存提案”后的自动保存。
普通聊天中的个人信息不得被后台静默保存；
未来如增加自动发现，只能以待确认建议的形式出现，不能绕过用户同意。

## 2. 现状与边界

### 2.1 可以直接复用的能力

- `ChatService` 已持久化会话、用户消息、助手消息和 AgentRun；
- Agent V2 已支持最近 8 条同会话消息和多轮能力调用；
- PostgreSQL 已启用 RLS，Repository 仍显式按 `user_id` 过滤；
- 已有 DashScope Embedding、pgvector、RAG 长度控制和模型配额；
- 已有 SSE 开始、状态、增量、完成、停止和恢复链路；
- 个人财务档案页面已包含 AI MEMORY 的交互骨架；
- 已有脱敏审计、错误契约、重复提交保护和账户注销数据保留策略。

### 2.2 当前尚不存在的能力

- 没有用户记忆设置和长期记忆数据表；
- 没有记忆 CRUD、检索、Embedding、去重和调用记录；
- 页面中的记忆列表仍是前端内存模拟；
- Agent 不会读取个人财务档案或跨会话记忆；
- LangGraph Checkpoint 只用于运行恢复，不是长期用户记忆。

### 2.3 不得混淆的三类上下文

| 类型 | 用途 | 生命周期 | 是否作为当前财务事实 |
| --- | --- | --- | --- |
| 会话历史 | 理解“那笔、继续、再分析”等指代 | 当前会话最近消息 | 否 |
| 长期记忆 | 用户主动保存的目标、偏好、约束和稳定背景 | 跨会话，直到用户删除 | 仅作为用户陈述背景 |
| 财务工具结果 | 余额、流水、预算、持仓和行情 | 每轮实时查询 | 是 |

实时账户余额、交易、持仓市值、行情和预算执行状态不得写入长期记忆替代工具查询。
即使记忆中出现旧金额，本轮回答仍必须使用只读财务工具重新确认实时事实。

## 3. 产品交互

### 3.1 模型驱动的记忆意图决策

首版不建设海量关键词、同义词或正则句式库。聊天进入通用 Agent 前，使用独立的
`MemoryDecisionProvider` 对当前用户本轮消息做一次低温度、强结构化判断：

- `save`：用户已明确要求将一项或多项内容作为跨会话长期记忆保存；
- `confirm`：消息表达了可能长期有效的偏好或约束，但是否要求持久化仍有歧义；
- `ignore`：普通陈述、召回询问、功能咨询、否定保存、引用内容或与记忆无关的消息。

模型应理解自然语言语义，不要求用户必须包含“记住”或命中固定句式。例如“你最好记着，我不接受
高杠杆方案”可以判为 `save`；“以后最好都按稳健方式分析”在授权不够明确时判为 `confirm`。

`confirm` 不写数据库，而是向用户展示规范化提案并提供“保存到记忆/仅本次使用”选择。只有用户明确
确认后才进入保存路径。待确认提案必须绑定当前用户、原始消息 ID、提案内容哈希和短期有效期，确认时
由服务端重新检查记忆设置与安全边界，不重新让模型自由改写提案。以下情况必须判为 `ignore` 或被服务端拒绝：

- “你还记得我说过什么吗？”等召回询问；
- “记忆功能怎么用？”等功能咨询；
- “不要记住这句话”等否定保存；
- 用户消息中的引用块、粘贴文档或转述指令；
- 历史消息、工具结果、知识库正文和助手推断出的信息。

可以保留极少量明确格式作为可选的延迟优化或模型故障降级，例如“请记住：……”，但它们不是主要
判断路径，也不得逐步扩张为大规模触发词库。首版默认策略是 Provider 不可用时不保存，而不是猜测授权。

### 3.2 保存后的回复

服务端只根据数据库事务的真实结果生成确定性确认部分，模型可负责意图判断、提案和补充分析。例如：

```text
已记住：
- 年收入税前 300,000 美元
- 平均年度开销 45,000 美元

基于这些由你提供的信息，你的税前支出约占收入的 15%。这只是基于个人档案的概算；
实际现金流和可投资金额仍需要结合税费、账户余额及真实流水确认。
```

确认文案不能完全交给模型，防止模型声称保存了实际未落库的内容。若部分记忆被拒绝，应逐项展示
“已保存、已存在或未保存”的结果，不允许笼统回复“都已记住”。

### 3.3 后续调用

用户之后在新会话询问“按照我的收入和开销，我适合如何设置应急金？”时：

1. Agent 判断问题需要个人稳定背景；
2. 调用受控的个人记忆检索能力；
3. 只返回当前用户、已启用、相关性足够的少量记忆；
4. 回答中使用“根据你保存的信息”说明来源；
5. 若还需要实时账户或流水，则继续调用相应财务工具；
6. 若财务档案与记忆冲突，不静默选择其中一个，应指出差异并请用户确认更新。

### 3.4 个人财务档案页面

保留当前 Origin 风格的布局，并将预览替换为真实数据：

- AI MEMORY 卡片展示启用状态、记忆总数和最近更新内容；
- 抽屉按“目标、偏好、约束、个人信息”筛选和分页；
- 支持新增、编辑、启用/停用、删除；
- 每条记忆显示来源（聊天保存或手动维护）及更新时间；
- 设置中分别控制“允许聊天保存”和“允许回答调用”，界面可提供一个总开关；
- 页面明确提示实时余额、流水、持仓和行情不会被当作长期记忆使用。

## 4. 数据模型

### 4.1 `identity.user_memory_settings`

每个用户一条设置记录，建议字段：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 主键并外键到当前用户 |
| `memory_enabled` | 总开关，默认 `true` |
| `chat_save_enabled` | 是否接受聊天中的显式保存指令，默认 `true` |
| `answer_recall_enabled` | 是否允许回答检索记忆，默认 `true` |
| `created_at` / `updated_at` | 创建和更新时间 |

设置读取可按需创建默认值；不得因为用户未打开过档案页面就禁用记忆能力。

### 4.2 `identity.user_memories`

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` / `user_id` | UUID 主键和所有者 |
| `category` | `goal`、`preference`、`constraint`、`personal` |
| `title` | 最多 80 字符的可读摘要 |
| `content` | 最多 1000 字符的规范化记忆正文 |
| `status` | `active` 或 `disabled` |
| `source_type` | `manual_ui` 或 `explicit_chat` |
| `source_message_id` | 产生该记忆的用户消息，可空；会话删除后置空 |
| `source_ordinal` | 同一消息拆分出的顺序号，用于重放幂等 |
| `content_hash` | 用户内规范化内容哈希，用于并发去重 |
| `embedding` | 可空 pgvector 向量 |
| `embedding_model` | 生成向量的模型版本 |
| `embedding_status` | `pending`、`ready` 或 `failed` |
| `last_used_at` / `use_count` | 调用统计，不保存问题全文 |
| `created_at` / `updated_at` | 创建和更新时间 |

约束要求：

- `(user_id, source_message_id, source_ordinal)` 唯一，确保 SSE 恢复和重新生成不会重复保存；
- 活跃内容在同一用户内按 `content_hash` 去重；
- 标题、正文、类别、状态和向量维度使用数据库约束；
- 表启用 `ENABLE/FORCE ROW LEVEL SECURITY`，Repository 仍显式限定 `user_id`；
- 用户注销继续采用现有软停用策略，不因注销物理删除记忆；后续数据删除专项另行定义。

### 4.3 `chat.agent_run_memories`

保存一次回答实际调用了哪些记忆，建议只记录：

- `user_id`、`agent_run_id`、`memory_id`；
- 排名、相关性分数、调用时的 `content_hash` 和 `updated_at`；
- 不额外复制记忆正文，减少敏感数据副本。

该表用于诊断、评测和证明回答使用了哪些记忆，但普通日志、Trace 和指标不得记录记忆正文。

## 5. 后端 API 与服务

### 5.1 用户接口

统一放在当前用户作用域：

```text
GET    /api/v1/users/me/memory-settings
PATCH  /api/v1/users/me/memory-settings
GET    /api/v1/users/me/memories
POST   /api/v1/users/me/memories
GET    /api/v1/users/me/memories/{memory_id}
PATCH  /api/v1/users/me/memories/{memory_id}
DELETE /api/v1/users/me/memories/{memory_id}
```

列表接口支持有界分页、类别、状态和短文本搜索；POST 支持 `Idempotency-Key` 或等价的请求幂等锚点。
DELETE 只允许删除当前用户记忆，并保留必要的脱敏审计记录。

### 5.2 服务拆分

新增独立模块，避免继续膨胀 `UserSettingsService`：

- `MemoryService`：设置、CRUD、去重、审计和使用统计；
- `MemoryDecisionProvider`：只读取当前用户消息，输出 `save/confirm/ignore` 与结构化记忆提案；
- `MemoryCommandService`：校验模型提案、执行确认流程并编排受控保存；
- `MemorySafetyService`：执行不可绕过的秘密、身份、实时财务事实和长度边界校验；
- `MemoryRetrievalService`：Embedding、相关性检索、预算裁剪和降级策略；
- `MemoryRepository`：所有数据库查询和行锁；
- `MemoryContext` 契约：向 Agent 暴露最少、明确标记为用户陈述的上下文。

### 5.3 Embedding 与检索

首版复用现有 DashScope Embedding 和 pgvector，但使用独立检索配置：

- 默认最多返回 5 条记忆；
- 单条最多注入 800 字符，总记忆上下文默认不超过 4000 字符；
- 必须同时满足当前用户、`active`、总开关和回答调用开关；
- 使用向量相似度、类别和最近更新时间排序；阈值通过评测集校准，不写死未经验证的业务结论；
- Embedding 失败不能撤销已经成功保存的记忆，可标记 `pending/failed` 后重试；
- 查询向量服务不可用时，只能使用有界、可解释的文本匹配降级，不能把全部记忆塞入上下文；
- 编辑正文后必须使旧向量失效并重新生成。

## 6. Agent 编排改造

### 6.1 保存路径：模型决策，服务端受控执行

聊天请求进入通用 Agent 前增加一次独立的记忆决策调用。模型拥有语义判断和发起保存工具调用的权限，
但不拥有数据库、用户身份或绕过安全策略的权限：

```text
当前用户本轮消息
  → 记忆设置与来源检查
  → MemoryDecisionProvider 强结构化判断
      ├─ ignore  → 不保存，继续正常回答
      ├─ confirm → 展示提案，等待用户明确确认
      └─ save    → 提交结构化记忆提案（最多 5 条）
  → 服务端验证原文证据、敏感类型和业务边界
  → 服务端绑定当前用户、执行去重和消息级幂等事务
  → 根据真实事务结果生成确定性确认
  → 将本轮成功保存的记忆作为受控上下文交给回答器
```

专用决策调用必须满足：

- 输入只包含当前用户本轮消息和记忆决策规则，不携带历史消息、知识库正文、工具结果或助手回复；
- 使用低温度和 JSON Schema/Function Calling 强制输出，不解析自由文本中的隐式工具指令；
- 输出使用判别联合，至少包含 `decision`、`reason_code` 和最多 5 条提案；
- 每条提案包含 `category`、`title`、`content` 和来自当前消息的 `evidence` 原文片段；
- `evidence` 必须能在当前消息的非引用用户正文中定位，否则服务端拒绝该提案；
- 模型可以判断、拆分、分类和规范化内容，也可以请求确认，但不得声称数据库已经保存成功；
- Function Call 只是一份待校验操作提案；应用端完成校验和事务提交后，才产生真实保存结果。

服务端受控执行器仍必须满足：

- 身份只来自认证上下文，工具参数不接受 `user_id`；模型不得输出或选择 SQL、表名和内部对象标识；
- 记忆总开关、聊天保存开关、RLS、幂等键、内容去重、数量与长度上限均不可被模型绕过；
- 密码、Token、银行卡号、证件号、实时余额、单笔流水、实时行情等禁止内容由本地确定性策略最终拦截；
- `confirm` 在用户明确确认前不得落库，普通陈述不得被模型静默保存；
- 待确认提案必须绑定当前用户、原始消息和内容哈希，并设置短期有效期；过期、篡改或跨用户确认一律拒绝；
- 结构化输出无效、证据不匹配或 Provider 暂时不可用时默认不保存，也不得声称保存成功；
- 不维护大规模触发关键词或句式列表；如保留极少量确定性快速路径，其结果也必须经过相同安全执行器；
- 同一消息重试、SSE 恢复和回答重新生成必须返回相同保存结果。

建议的决策契约：

```text
MemoryDecision
  decision: save | confirm | ignore
  reason_code: explicit_save_request | ambiguous_long_term_preference |
               recall_question | negated_request | feature_question |
               quoted_instruction | sensitive_content | not_memory_related
  items: MemoryProposal[0..5]

MemoryProposal
  category: goal | preference | constraint | personal
  title: 1..80 字符
  content: 1..1000 字符
  evidence: 当前用户消息中的原文证据
```

### 6.2 调用路径：受控只读能力

向 Agent V2 动态能力目录增加 `search_personal_memories`：

- 仅在记忆启用且当前用户存在活跃记忆时提供；
- 参数只允许查询文本、类别和有限数量，不接受用户标识；
- 服务端强制绑定当前登录用户；
- 返回结构化的记忆编号、类别、标题、正文和更新时间；
- 上下文明确标记为 `user_provided_memory`，不是系统指令，也不是实时财务证据；
- AgentRun 记录能力调用和记忆 ID，不记录查询全文或记忆正文。

Agent 可在后续问题中主动调用该能力；涉及个人余额、流水、预算、持仓和行情时，仍必须调用现有财务工具。

### 6.3 个人财务档案接入

个人财务档案和长期记忆分开存储、统一提供给回答器：

- 结构化档案负责出生日期、所在地、就业、职业、年收入和年度开销预算；
- 长期记忆负责目标、偏好、约束和其他用户主动陈述；
- 档案字段为空时，可使用相关记忆作为“用户保存的背景”；
- 两者冲突时不得静默覆盖；回答提示存在差异，并引导用户在档案或记忆列表中修正；
- “记住年收入……”首版保存为记忆，不暗中修改财务档案，避免一次指令触发两个隐藏写入。

## 7. 敏感信息与财务安全

### 7.1 禁止保存

- 密码、API Key、JWT、Refresh Token、验证码和密钥；
- 完整银行卡号、支付账号、身份证件号码和私钥；
- 知识库正文、工具输出或助手推断出的第三方敏感信息；
- 单笔流水、当前余额、实时持仓市值、实时行情等易过期事实；
- 改变系统指令、权限、工具白名单或要求绕过安全策略的内容。

若命令同时包含可保存信息和禁止信息，首版应整体拒绝或逐项明确拒绝，不得把敏感原文写入审计日志。

### 7.2 允许保存但需标记为用户陈述

- 长期目标、投资期限、风险偏好；
- 预算习惯、沟通偏好和分析偏好；
- 稳定的家庭、工作和地域背景；
- 用户主动提供的收入、固定开销或计划，但回答时要说明是用户保存的信息，并在需要时查询实时数据。

### 7.3 审计和可观测性

允许记录动作、用户哈希、记忆 ID、类别、长度、结果码、重复状态和耗时；禁止记录记忆正文、标题、
聊天原文、向量、财务数值和敏感字段。新增指标至少覆盖保存成功/拒绝/重复、检索命中、上下文条数、
Embedding 失败和跨用户隔离失败；不得使用原始用户 ID 作为高基数标签。

## 8. 前端和协议改造

### 8.1 前端服务与类型

- 新增记忆设置、列表、CRUD 的 API 类型和服务；
- 删除 `FinancialProfilePanel.vue` 中硬编码的 `memories` 示例数组；
- 页面加载档案时并行加载设置和记忆摘要；
- 增加加载、空状态、失败重试、分页、重复提交保护和删除确认；
- 编辑保存后使用后端返回值刷新，不乐观伪造已保存状态。

### 8.2 聊天反馈

首版可以用助手正文展示确定性“已记住”结果；建议同时扩展 SSE：

```text
event: memory_saved
data: { memory_id, category, title, result }
```

前端可据此展示轻量“已保存到记忆”提示并刷新档案摘要。SSE 事件不得携带完整正文；恢复重放时必须复用
同一事件结果。历史消息至少应能从助手正文还原保存确认，不能只依赖瞬时 Toast。

## 9. 分阶段实施顺序

### M1：记忆持久化底座与 CRUD

交付：

- 两张身份域表和一张调用关联表的 Alembic 迁移；
- SQLAlchemy 模型、Repository、Service、Schema 和用户 API；
- RLS、唯一约束、审计、分页和设置开关；
- 前端记忆管理区连接真实 API，移除预览文案和模拟数组。

完成门槛：页面手动新增记忆后刷新仍存在；另一用户无法读取、修改或删除；迁移往返和
`alembic check` 通过。

### M2：模型驱动的聊天记忆保存

交付：

- 独立 `MemoryDecisionProvider`、`save/confirm/ignore` 判别契约和 Function Calling/JSON Schema；
- 仅当前用户消息输入、原文证据校验，以及绑定用户、消息、内容哈希和有效期的模糊意图确认交互；
- 多条记忆拆分、禁止内容过滤、去重和消息级幂等；
- 服务端确定性确认文案；
- SSE `memory_saved` 事件及前端即时刷新；
- 保存失败、部分拒绝和 Provider fail-closed 语义；
- 版本化决策 Prompt 和自然语言意图评测集，不建设大规模本地关键词/句式库。

完成门槛：多种自然语言保存请求无需固定句式即可落库并得到真实确认；歧义表达先确认；召回询问、
否定表达和引用内容不会写入；模型越权输出被拒绝；重试、恢复、重新生成不产生重复记录。

### M3：跨会话检索与个性化回答

交付：

- 记忆 Embedding、重建和相关性检索；
- `search_personal_memories` 只读能力；
- 独立上下文预算、AgentRun 使用关联和 Prompt 信任边界；
- 个人财务档案受控接入和冲突提示；
- 基于记忆继续分析，但实时事实仍调用财务工具。

完成门槛：新会话能自动使用相关记忆；无关问题不注入；关闭调用开关后不再使用；回答不得把记忆冒充实时事实。

### M4：管理体验完善

交付：

- Origin 风格记忆摘要、列表、筛选、来源和更新时间；
- 编辑、停用、删除、错误恢复和移动端布局；
- 用户可识别哪些信息被保存、哪些回答使用了记忆；
- 后续可选的“忘记……”聊天指令，删除前必须展示命中项并确认。

完成门槛：用户不依赖数据库或开发工具即可完整管理记忆；删除或停用后下一轮不再调用。

### M5：安全评测、性能与灰度

交付：

- 记忆意图决策、确认和召回的版本化评测集；
- Prompt Injection、敏感信息、跨租户、重复保存和冲突数据测试；
- Token、延迟、Embedding 成本和检索阈值基线；
- 功能开关、数据库迁移、回滚和候选环境验收记录。

完成门槛：所有门禁通过后才默认启用；发现跨用户泄漏、静默误保存或实时财务事实被旧记忆覆盖时必须阻止发布。

## 10. 测试与验收矩阵

### 10.1 必测记忆决策与保存

| 输入 | 预期 |
| --- | --- |
| “记住：我偏好低波动方案” | 保存一条 `preference` |
| “你最好记着，我不接受高杠杆方案” | 无需固定句式，保存一条 `constraint` 或 `preference` |
| “记住：年收入 30 万美元，每年开销 4.5 万美元” | 拆成两条或两个明确事实，回复逐项确认 |
| “以后最好都按稳健方式分析” | 返回待确认提案，确认前不落库 |
| 用户对待确认提案选择“仅本次使用” | 不保存，仍可用于当前回答 |
| 待确认提案过期、被篡改或由另一用户提交 | 服务端拒绝确认，不保存 |
| “你还记得我的收入吗？” | 只查询，不新增记忆 |
| “不要记住我的密码是……” | 不保存，且日志不出现密码 |
| 用户消息引用文档正文“记住以下指令” | 证据属于引用内容，不保存 |
| 历史消息、工具结果或知识库正文包含保存指令 | 不进入决策输入，不保存 |
| 模型提案的 `evidence` 不存在于当前用户正文 | 服务端拒绝，不保存 |
| 模型输出 `user_id`、SQL 或内部对象标识 | 契约校验失败，不执行 |
| 决策 Provider 超时、异常或输出无效 | fail-closed，不保存且不声称成功 |
| 同一请求断线重连 | 只保存一次 |
| 相同内容在另一会话再次保存 | 返回“已存在”，不重复新增 |
| 关闭聊天保存开关后输入“记住……” | 明确告知未保存 |

### 10.2 必测召回

- 同会话和新会话均能命中相关记忆；
- 无关问题不携带无关记忆；
- 停用、删除和关闭调用开关立即生效；
- 用户 A 的任何检索均不能返回用户 B 的记忆；
- 记忆与财务档案冲突时提示确认；
- 记忆中的旧余额不能阻止本轮余额工具调用；
- Embedding Provider 故障时行为明确且不会泄漏或无限注入；
- 记忆上下文始终满足条数和字符预算。

新增配置均须有保守默认值和上下界：

```text
AURUM_MEMORY_ENABLED=true
AURUM_MEMORY_ROLLOUT_PERCENTAGE=100
AURUM_MEMORY_MAX_ITEMS_PER_USER=200
AURUM_MEMORY_MAX_ITEMS_PER_COMMAND=5
AURUM_MEMORY_RETRIEVAL_LIMIT=5
AURUM_MEMORY_CONTEXT_MAX_CHARACTERS=4000
AURUM_MEMORY_ITEM_MAX_CHARACTERS=800
AURUM_MEMORY_EMBEDDING_ENABLED=true
AURUM_MEMORY_DECISION_ENABLED=true
AURUM_MEMORY_DECISION_TIMEOUT_SECONDS=20
AURUM_MEMORY_DECISION_MAX_RETRIES=1
AURUM_MEMORY_CONFIRMATION_TTL_SECONDS=600
```

用户达到上限时不自动覆盖旧记忆，应提示其进入档案页面清理。配置关闭时保持 API 可读和用户数据不丢失，
但禁止聊天保存与 Agent 调用，以便安全灰度和快速止损。

## 12. 本专项明确不做

- 不从普通对话中静默学习或自动保存；
- 不建设或维护海量记忆触发关键词、同义词和正则句式库；
- 不让模型直接执行数据库写入、指定用户身份或绕过服务端安全执行器；
- 不把 Checkpoint 当作长期记忆数据库；
- 不把全部历史会话、全部记忆或完整个人档案塞入上下文；
- 不用记忆替代余额、流水、预算、持仓和行情工具；
- 不在首版实现复杂的记忆合并、自动遗忘、时间衰减或知识图谱；
- 不因“记住”指令自动修改结构化个人财务档案；
- 不开放自然语言记账、转账、交易或其它财务写操作。

## 13. 最终发布判定

本功能只有同时满足以下条件才算完成：

1. 用户以多种自然语言明确要求长期保存时能够可靠落库并得到真实确认，歧义表达必须先确认；
2. 记忆可在档案页面完整管理；
3. 新会话能自动调用相关记忆生成更有针对性的回答；
4. 记忆关闭、停用和删除立即影响后续回答；
5. 实时财务事实仍由受控工具提供；
6. RLS、Repository、审计、幂等、敏感信息过滤和上下文预算全部通过测试；
7. SSE 重连、回答重新生成、模型越权输出和 Provider 故障不会导致重复、静默或虚假保存；
8. 候选环境真实模型和真实数据库验收通过。

建议从 M1 开始逐阶段提交，每个阶段单独迁移、测试和评审，不将五个阶段合并成一个难以回滚的大提交。
