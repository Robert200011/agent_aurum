# Aurum Agent 当前阶段功能完善建议

> 形成日期：2026-08-07  
> 适用范围：阶段一至阶段六工程开发已完成、阶段七尚未启动时的功能完善与实施排序建议。  
> 依据：`project_introduction/` 下的总体设计、架构说明、阶段五/阶段六验收文档、部署指南及最新交接记录。

## 1. 当前判断

Aurum Agent 已具备较完整的个人财务投资 Agent 基础能力：多租户与 RLS 隔离、个人财务账本、知识库入库和可信 RAG、只读财务工具、投资风险策略、会话与 SSE、审计、限流配额、日志脱敏、可观测性、备份恢复以及蓝绿发布演练。

当前优先事项不应是立即增加更多 Agent 或开放写操作，而应优先补齐生产可用性、运行可靠性和可复用的产品闭环。阶段六功能已合入 `master`，但真实候选环境上线验收、正式生产发布及容量基线仍需完成。

### 1.1 2026-08-11 Agent V2 落地状态

财务问答已升级为 `finance-capability-agent-v2`：外接模型是主要规划器，运行时动态提供只读
财务、个人知识和无需私有数据回答能力；支持多轮工具调用、统一服务端时间语义及会话历史。
所有用户数据仍经服务端身份绑定、权限和参数校验，最终回答继续接受财务事实、引用、安全输出
和投资风险校验。用户完成界面验收后，旧规则规划器、旧 JSON 模型规划器、旧图分支、关键词
日期解析和对应开关已删除；历史 Checkpoint 只保留无执行逻辑的类型路径兼容层。

### 1.2 2026-08-13 设置中心专项进度

设置中心阶段一至阶段三已完成个人档案、安全中心、财务偏好、显示偏好、帮助与关于信息，
并支持财务账户查看及新交易默认账户设置。登录设备和“退出其他设备”需求已取消。

- 设置中心阶段四“通知与提醒设置”暂缓，不纳入当前开发范围；
- 设置中心阶段五不再包含个人数据导出和数据使用说明；
- 阶段五仅保留账户注销，并已实现风险提示、用户名确认、当前密码验证和最终操作确认；
- 注销采用软停用，不物理删除个人财务或知识库数据；完成后撤销全部刷新令牌、使既有访问令牌
  失效并结束当前登录；
- 账户注销仅保留必要的高风险操作审计，不扩大通用审计测试范围。

### 1.3 2026-08-13 设置中心阶段六收尾状态

设置中心阶段六的体验完善与自动化验收已完成，设置中心专项进入稳定收尾状态：

- 完善窄屏布局，账户摘要、账户选项、操作按钮和档案字段可在 320px 起的视口中正常重排；
- 增加设置资料和财务账户加载状态、失败提示、就地重试及既有空状态；
- 对资料、偏好、默认账户和账户注销操作增加客户端重复提交保护；
- 补充可展开模块的可访问名称、动态状态播报、注销确认打开后的输入焦点，以及减少动态效果
  的系统偏好支持；
- 全局快捷键不再拦截输入框、文本域、下拉框或可编辑区域中的正常输入；
- 注销确认关闭后清空用户名、密码和风险确认状态，不在前端保留敏感输入；
- 核心前端回归覆盖加载失败恢复、单模块展开、敏感金额、注销二次确认和重复提交保护，
  不扩大通用审计测试范围。
- 已使用隔离的浏览器接口响应完成桌面端设置展开、注销确认焦点与提交门槛，以及 320px 移动
  视口可操作性验收；真实账户停用与凭证撤销语义由后端服务测试覆盖。

设置中心阶段四仍为暂缓项，不影响设置中心阶段一、二、三、五、六按当前范围完成。

## 2. 优先级建议

| 优先级 | 建议方向 | 目标 |
| --- | --- | --- |
| P0 | 候选环境真实验收 | 验证阶段六在真实依赖、目标机器和真实模型下的可靠性、性能与成本 |
| P1 | 生产可观测性闭环 | 将现有监控能力提升为可长期运营、可追责、可排障的体系 |
| P1 | 多实例 SSE 可靠续传 | 支持 API 横向扩展、连接重连和容器重启后的运行中事件恢复 |
| P2 | 月度/季度个人财务报告 | 在只读安全边界内形成高价值用户功能闭环 |
| P2 | 投资组合风险报告 | 输出基于受控财务证据的风险事实与风险提示，不生成确定性买卖结论 |
| P2 | 知识库运营与质量诊断 | 提升文档入库、检索、引用和评测的可运营性 |
| P3 | 受控自然语言写操作专项设计 | 先形成草案、确认、审计、幂等与补偿机制，再逐步开放写能力 |
| P3 | 动态套餐、计费与配额 | 在真实容量与模型成本数据形成后，产品化成本治理 |

## 3. P0：候选环境真实验收

阶段六完成了本地发布、恢复、观测和负载演练，但正式上线前仍需在候选环境中使用真实依赖完成验证。

### 3.1 验收范围

- 使用真实 PostgreSQL、Redis、MinIO、Embedding、Reranker 和 Chat 模型 Provider；
- 使用目标服务器规格、正式或接近正式的网络拓扑和配置；
- 复跑真实 Provider 冒烟、版本化评测、发布检查及 `single-node-release` 压测；
- 校准 Token 预算、模型延迟、缓存收益、限流阈值和 Worker 并发；
- 验证备份、隔离恢复、蓝绿切流与回滚在候选环境中的可复现性。

### 3.2 重点指标

- API 5xx 比例低于 1%；
- P95 延迟相较锁定基线回退不超过 20%；
- SSE 长连接、事件完成与客户端恢复稳定；
- Redis 配额、并发租约、缓存与 Celery 队列无持续增长；
- 数据库连接池和 Worker 资源无泄漏；
- 跨用户、跨项目、跨会话的数据泄漏为零；
- RAG 引用、财务数值 Grounding、风险提示与安全输出评测不回退。

### 3.3 发布前门禁

正式切流前应由授权人员审核并留存以下证据：

1. 候选环境真实依赖冒烟结果；
2. 容量压测与性能基线；
3. 备份和隔离恢复报告；
4. 评测门禁结果；
5. 发布 Manifest、镜像 digest、配置审计和回滚演练结果；
6. 正式 TLS、密钥管理、最小权限账号与异地备份配置确认。

### 3.4 Agent 财务问答灵活性与简洁回答门禁

现有财务问答已具备只读工具、证据快照和 Grounding 校验，但仅依赖固定关键词选择工具时，
口语化问题可能被降级为宽泛汇总。例如“最近一笔消费花了多少钱、用途是什么”需要单笔流水，
不能由区间财务摘要替代。该问题应作为新增业务功能前的产品正确性门禁。

- 对余额、明确时间范围和高风险投资等高置信度问题继续使用确定性规则；
- 对规则只能给出默认汇总或无法识别的表达，使用模型生成结构化只读工具计划；
- 模型计划必须经过 Pydantic 判别联合、工具白名单、参数上限、租户归属和服务端日期校验；
- 增加 `get_latest_transaction`，支持最近、最后、上一笔收入或支出的金额、分类和用途查询；
- 默认第一句直接回答问题，单一事实控制在一至三句话，详细分析仅在用户明确要求时展开；
- Provider 或计划解析失败时回退到确定性路径，不允许模型生成 SQL、用户标识或写操作；
- AgentRun 记录规则/模型规划方式、路由原因和置信度，但不记录问题全文或模型规划正文；
- 将口语化同义问法、伪造工具参数、最近一笔流水和简洁回答纳入版本化评测。

## 4. P1：生产可观测性闭环

当前已具备白名单日志、统一脱敏、OpenTelemetry、Prometheus、Grafana 与告警基础。下一步应将其固化为长期运行能力。

### 4.1 建议补强项

- 建立长期可检索的 Trace 后端，并控制访问权限和留存周期；
- 关联 `request_id`、`agent_run_id`、conversation 等运行标识，但不得记录用户问题全文、财务明细、文档正文、Token、密码或密钥；
- 分段统计 Agent 链路：问题分类、工具调用、检索、重排、生成、引用校验、财务 Grounding、风险校验；
- 增加按模型、路由类别、工具类别和用户配额维度的 Token、缓存和成本指标；
- 增加引用缺失、Grounding 失败、输出安全拦截、模型重试、超时和队列堆积等质量指标；
- 固化告警等级、排障手册、发布后观察窗口和值班响应流程；
- 汇聚跨 API 进程和 Celery Worker 的指标，避免仅以单进程指标判断系统状态。

### 4.2 隐私与安全边界

可观测性不应成为敏感数据副本。日志、Trace 和指标中禁止保存：

- 用户问题全文；
- 文档正文、Chunk 内容与模型上下文；
- 银行卡号、交易备注、账户明细；
- API Key、JWT、Refresh Token、数据库 URL 或任何密码；
- 高基数且可直接识别用户的原始标识。

## 5. P1：多实例 SSE 与运行事件可靠续传

当前最终消息、引用、财务证据和 Checkpoint 已可持久化，但运行中 SSE 事件重放协调器主要面向单 API 进程。多实例部署、负载均衡切换或容器重启时，用户可能无法无缝恢复实时进度。

### 5.1 建议目标

- 支持客户端基于 `agent_run_id` 与事件游标恢复运行中事件；
- 支持 API 实例无状态化，任意实例均可提供事件续传；
- 支持短暂网络中断、网关重连和 API 容器滚动重启后的恢复；
- 为事件设置 TTL、最大回放窗口和清理策略，防止 Redis 或数据库无限增长；
- 保持 PostgreSQL 中的最终回答、引用、财务证据和审计记录为唯一业务权威来源。

### 5.2 可选实现方向

可在详细设计阶段比较以下方案：

1. Redis Streams：适合短期实时事件、消费者游标和多实例回放；
2. 持久化运行事件表：适合审计、长时间回放和强一致的历史查询；
3. 独立事件总线：适合未来多服务、多区域或更复杂异步编排。

第一版建议优先采用与现有 Redis 基础设施兼容的 Redis Streams，并保留最终结果写入 PostgreSQL 的既有流程。

## 6. P2：月度/季度个人财务报告

这是建议优先实现的业务功能。它能直接复用当前只读财务工具、时间范围解析、预算状态、异常检测、币种换算、财务证据、风险提示、会话审计和报告生成能力，同时不突破当前安全边界。

### 6.1 报告内容建议

- 本期收入、支出、净现金流和期末账户余额；
- 收支类别构成与主要变化；
- 与上一周期的同比、环比或区间对比；
- 预算执行情况、超支风险与月末预测；
- 异常交易、异常支出趋势和缺失数据提示；
- 多币种汇总、汇率来源和换算不确定性说明；
- 数据截至时间、统计账户范围、使用工具和财务证据快照；
- 明确分区展示“个人财务事实”“分析发现”“可执行建议”“风险和局限”。

### 6.2 实施建议

- 首版采用异步任务生成，避免长报告阻塞聊天请求；
- 报告应版本化保存，记录生成参数、数据截止时间、证据快照和生成状态；
- 支持 Markdown 或 PDF 导出，并做严格的下载权限校验；
- 报告中的数值必须来自确定性工具输出，模型仅负责组织语言和解释；
- 报告失败应支持重试，但重试必须可审计且避免重复创建无意义版本；
- 可先支持“手动生成某月报告”，随后再评估计划任务和提醒能力。

## 7. P2：投资组合风险报告

投资组合风险报告应严格限制在“可验证的风险事实、数据局限与风险提示”范围内，避免预测未来收益、承诺回报或给出确定性买卖结论。

### 7.1 首版建议覆盖

- 资产类别、单标的、行业、市场和币种集中度；
- 单标的持仓成本、当前行情、未实现盈亏和历史表现；
- 现金比例、流动性概览与集中度提示；
- 缺失行情、过期行情、汇率换算与数据完整性提示；
- 投资期限、风险承受能力等用户未提供信息的明确缺口说明；
- 统一风险提示及“非个性化投资建议”边界。

### 7.2 后续能力应以数据质量为前提

波动率、相关性、最大回撤、VaR、压力测试等统计指标可作为后续候选能力，但必须先明确：

- 历史行情来源、授权、覆盖范围与更新频率；
- 复权、币种、停牌、缺失值和公司行动处理；
- 计算口径、时间窗口与可复现性；
- 结果展示中的误差、局限和风险说明。

在缺少可靠历史数据与计算基线时，不应让模型直接生成此类数值。

## 8. P2：知识库运营与质量诊断

现有系统已有文档版本、异步入库、解析、Chunk、Embedding、Hybrid Retrieval、Reranker、引用校验和评测能力。下一步可提升管理员运营体验与检索质量可见性。

### 8.1 建议能力

- 文档上传、解析、Embedding、发布、失败重试的状态面板；
- 文档解析失败率、任务重试次数与失败原因聚合；
- Chunk 数量异常、重复内容、超长/过短 Chunk 和低质量文本识别；
- 文档版本、来源更新时间和内容过期提醒；
- 无答案率、低引用率、引用校验失败率、检索/重排耗时趋势；
- 按项目、知识库或文档批量重索引；
- 面向版本化评测集的检索和回答回归趋势展示；
- 审计级检索查询，但仍需避免展示其他用户、其他项目或敏感原文。

### 8.2 设计原则

- 质量诊断数据与用户业务数据必须保持项目和租户隔离；
- 管理面展示指标优先使用汇总、哈希或脱敏样本；
- 文档重索引需要版本化发布，未完成校验的新版本不得替换现有可用版本；
- 运营功能不得绕过原有的权限、RLS、审计与对象访问校验。

## 9. P3：受控自然语言写操作专项设计

自然语言记账、预算修改、流水删除和持仓调整具有明显高风险，不能直接将现有只读 Agent 工具改为写工具。应先完成独立设计和专项验收。

### 9.1 建议的渐进路线

1. Agent 只解析意图并生成“操作草案”；
2. 前端展示字段级变更：金额、账户、类别、日期、备注及影响范围；
3. 用户显式确认后，受控应用服务执行写入；
4. 写入使用幂等键，防止双击、网络重试或 SSE 重连导致重复记账；
5. 保存完整审计记录：草案、确认人、确认时间、请求来源、写入结果和失败原因；
6. 提供撤销或补偿能力，并限制可撤销的操作范围；
7. 先开放“新建草稿流水”，再评估正式记账、预算修改、持仓调整和删除操作。

### 9.2 必须具备的控制点

- Human-in-the-loop 显式确认；
- 权限、RLS 和可信运行上下文；
- 参数白名单与服务端业务规则校验；
- 幂等、并发控制、审计、撤销/补偿；
- 写入前后余额、预算和持仓一致性校验；
- 失败恢复、重放测试和跨用户隔离测试；
- 禁止模型直接执行 SQL 或绕过应用服务写入数据库。

## 10. P3：动态套餐、计费与配额治理

阶段六已经实现第一版 Redis 配额、Token 预留与实际结算、并发租约和安全检索缓存。现阶段配额仍以环境变量为主，建议在真实容量和成本数据形成后再产品化。

### 10.1 后续候选能力

- 按用户、套餐、项目、模型或功能维度配置请求与 Token 配额；
- 管理员用量、缓存命中、队列消耗和成本趋势面板；
- 高成本模型、长报告、批量上传和重索引的额度控制；
- 成本异常、突发流量、缓存失效和配额耗尽告警；
- 受控的配额动态调整与变更审计；
- 对普通问答、财务报告和高复杂度任务实施不同的成本策略。

### 10.2 前置条件

- 候选环境的真实 Provider 延迟、Token 使用和账单数据；
- 明确用户量、并发、文档规模、业务 SLO 和成本预算；
- 已验证限流、缓存和并发租约在目标负载下的行为。

## 11. 推荐实施顺序

1. 候选环境真实验收与性能、成本、容量基线；
2. Agent 财务问答灵活路由、单笔流水能力和简洁回答质量门禁；
3. 生产可观测性闭环；
4. 多实例 SSE 和运行事件可靠续传；
5. 月度/季度个人财务报告；
6. 投资组合风险报告；
7. 知识库运营与质量诊断；
8. 自然语言记账“草案 + 确认”专项设计与验收；
9. 基于真实规模证据评估动态配额、计费、API 横向扩展、Worker 队列拆分、托管数据库或多 Provider 容灾。

## 12. 不建议提前引入的复杂度

在尚未获得真实用户量、并发、成本和可用性数据前，不建议为了“未来可能需要”而提前引入：

- Kubernetes；
- 多地域双活；
- 跨云灾备；
- 复杂自动弹性伸缩；
- 多 Provider 自动容灾；
- 复杂计费系统；
- 直接由模型驱动的财务写操作。

上述能力应由真实业务规模、明确 SLO、合规要求和成本模型驱动，而不是作为阶段七之前的预设复杂度。

## 13. 结论

推荐将“月度/季度个人财务报告”作为下一项最优先的业务功能：用户价值直观，能够复用现有确定性财务工具、证据、审计和风险控制能力，并且始终保持只读边界。

不过，在开始该功能前，应先完成候选环境真实验收、Agent 财务问答灵活路由与简洁回答门禁，
再补强生产可观测性和多实例 SSE 续传能力。这样可以确保后续产品能力建立在已验证的问答正确性、
运行成本、可靠性和数据隔离基础之上。
